# 键位 → 协程 → Lua 宏执行：架构与实现计划

## 核心决策：用 Lua 协程，不用线程

**推荐：单一调度 worker 线程持有唯一 `lua_State`，每个激活键位 = 一个 Lua 协程（`lua_newthread`），协程通过 yield 命令表与 C++ 调度器握手。**

理由（针对本项目的硬约束）：

1. **`lua_State` 非线程安全** —— OS 线程方案必须每线程一个独立 state，脚本/绑定/枚举全要重复加载；共享 C++ 状态（linux.cpp 的 `tracked_x/y` 光标追踪、`uinput_fd`）还得加锁，uinput 的 `emit()+SYN` 写序列被并发交错会直接破坏输入协议。
2. **toggle 取消** —— "按一次开始、再按一次结束"（`loop.times=-1`）在协程方案下 = 丢 registry 引用 → GC 回收，瞬时且无副作用；OS 线程取消（强制终止/协作标志）又危险又复杂。
3. **宏负载全是"移动/点击/等待"** —— 协作式 yield 天然够用，零线程创建开销、无 join/清理负担；"防阻塞"由**非阻塞调度器 + 分帧命令执行**保证，而不是靠并发。
4. **唯一线程拥有 Lua 也是 wxWidgets 边界的要求** —— GUI 线程之外只有 worker 碰 Lua，worker→GUI 走 `wxQueueEvent`，线程模型清晰。

什么时候才该用 OS 线程：需要真正 CPU 并行的独立宏、或 handler 必须阻塞外部系统调用。本项目不出现。注意：**协程本身不防阻塞**——真正防阻塞的是"所有耗时操作必须 yield/分帧 + 调度器永不做长操作"。

## LuaBridge 版本决策：保持 2.10，不升 3.0-rc12

- 协程核心（`lua_newthread`/`lua_resume`/`lua_yield`/`luaL_ref`）全是 Lua C API，调度器不依赖 LuaBridge；LuaBridge 只负责枚举表（现有 `script_binding.cpp` 是纯 C API 写的）与未来 `mouse::*` 函数绑定。
- 已核实 2.10（`FuncTraits.h` 的 `Invoke::run`）与 3.0（`CFunctions.h` 的 `function<...>::call`）的普通函数调用路径**均无 `lua_call` 边界**，C++ 函数内 `lua_yield` 两者都合法——2.10 没有功能缺口（只有 metamethod/getter 路径才不能 yield）。
- 3.0-rc12（kunitoki/LuaBridge3）仍是 pre-release（2025-06-03），API 大面积重构（`LuaRef::operator()` → `LuaResult`、`enableExceptions` 显式化、`Nil`→`LuaNil`、`Stack<T>::push` 签名变化），资料少；其卖点（C++20 协程集成 `CppCoroutine`/`LuaCoroutine`、性能优化）当前命令流架构用不上。
- 结论：维持 CMakeLists 现有 FetchContent（vinniefalco/LuaBridge tag 2.10）；待 3.0 正式版且确有"Lua 直接驱动 + C++ 侧协程集成"需求时再评估迁移。

## 目标架构（命令流握手模型）

```
worker 线程 tick 循环 (每 ≤4ms):
  1. 处理 GUI 请求队列 (reload_config / stop_all / shutdown)
  2. 对每个绑定键: is_key_pressed() 边沿检测
     - loop 键 按↓ : active ? 取消(toggle off) : spawn
     - 非 loop 键 按↓ : 未 active 才 spawn（重复按忽略）
  3. 推进活跃协程 + 命令执行器:
     - pending 命令完成 (translate 分帧走完 / click 已发 / delay 到期) → lua_resume 协程
     - resume 返回 LUA_YIELD → 读栈顶命令表 → 进入命令执行器
     - 返回 LUA_OK → 协程结束 → unref
     - 返回错误 → log + unref（含看门狗触发）
  4. sleep 到下一截止时间 (≤4ms, 条件变量 wait_for)
```

每个键的协程体 = C++ 生成的 driver 函数（包装用户 `run()`，`loop.times/delay` 内联进 driver）：

```lua
-- 用户 val 代码（定义 run()）内联在函数头
local n = 0
while true do
    __dispatch(run())            -- 裸 C 函数：yield 命令表给 C++ 调度器
    n = n + 1
    if times >= 0 and n >= times then break end
    __dispatch({command = "delay", vals = {delay}})
end
```
非 loop 键：times=1、delay=0。命令表目前支持 `translate{angle,dist,time_ms}`、`click{btn}`、`delay{ms}`；后续可扩展 `press/release/wheel/move_to`，并为"Lua 直接驱动"（Lua 内 while + 调 C++ API + sleep）留好接口——yield API 与命令流协议复用同一套。

## 关键 C API 序列

```c
// 创建协程（run_ref 为 luaL_ref 存的用户 run 函数；driver 已在 lua_State 上编译为函数）
lua_rawgeti(L, LUA_REGISTRYINDEX, driver_ref);   // 主栈: driver fn
lua_State* T = lua_newthread(L);                 // 主栈: fn, T
lua_xmove(L, T, 1);                              // T 栈: fn
int st = lua_resume(T, L, 0, nullptr);
if (st == LUA_YIELD) read_cmd_table(T);          // 命令表在 T 栈顶

// 裸 C yield 函数（__dispatch）—— LUA_MASKCOUNT 看门狗在每次 resume 前清零静态计数
static int lua_dispatch(lua_State* T) {
    // 参数 1 是命令表，留在栈顶
    return lua_yield(T, 1);                      // 5.4 合法（C 帧 nny==0）
}

// 取消 = 丢弃唯一引用（协程只被该引用持有 → GC 回收，含其 upvalue）
luaL_unref(L, LUA_REGISTRYINDEX, ref);

// 看门狗：防 `while true do end` 卡死 worker
static void runaway_hook(lua_State* L, lua_Debug*) {
    if (++instr_since_yield > BUDGET) { instr_since_yield = 0; luaL_error(L, "script runaway"); }
}
lua_sethook(L, runaway_hook, LUA_MASKCOUNT, BUDGET);  // BUDGET≈5e7 指令
// 每次 lua_resume 返回后 instr_since_yield = 0（预算 = "两次 yield 之间指令数"，粗粒度可接受）
```

## 风险与缓解

1. **yield 型 API 统一用裸 `lua_pushcfunction` 注册**（行为最确定、零模板开销；`__dispatch` 等 yield API 走这里）。已核实 2.10 与 3.0 源码：普通函数调用路径均无 `lua_call` 边界，C++ 函数内 `lua_yield` 两个版本都合法，但**仅限普通函数调用**——作为 metamethod/getter 被调用（经 `lua_call`）时不能 yield。LuaBridge 只用于纯值/枚举暴露（现有 `mouse_btn`/`wheel_rotation`）与非 yield 的 C++ 函数。
2. **Lua 死循环卡死整个 worker** → `lua_sethook` 预算看门狗（见上），误杀面窄：合法宏每次 resume 只跑少量指令。
3. **现有 `move_to/translate(time_ms)` 是阻塞 Sleep 循环**（win.cpp:146、linux.cpp:250/319）→ 必须重构为分帧 step，否则调度器被卡死。
4. **边沿检测漏检/双发**（4ms 轮询快速连按）→ prev 状态机只认物理 keydown 边沿；非 loop 键 active 时忽略再次按下。
5. **退出顺序** → `OnExit` 里 join 先于 GUI 销毁；`lua_close` 只能在 worker 线程；worker 用 `wait_for` 而非无界 sleep 防 join 死锁。

## 验证

1. `cmake --build build --config Debug`（或现有构建流程）编译通过。
2. 手动功能测试：编辑 `%APPDATA%\moused\config.toml`，把 `[F1].enabled=true`（loop.times=-1、delay=0.05、click LMB）→ 运行 moused → 按 F1 开始连点、再按停止；再启用 `[L]`（translate 平滑移动）→ 按住期间按其他键 → 确认各宏互不阻塞、UI 不冻结。
3. 看门狗测试：某键 `val` 写 `while true do end` → 数秒内被掐死并写日志，其他键位不受影响。
4. 边界测试：非 loop 键快速连按 → 只执行一次不重入；loop 键 toggle 快速开关无泄漏（观察日志无错误）。
